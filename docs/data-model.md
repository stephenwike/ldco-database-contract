# Data model notes

Human context for the schemas in `src/contract/collections/`. Those files are generated by `npm run contract:infer` and describe *what is*; this file records *why*. Add a section per collection as decisions are made.

## dances

Database `ldco`, collection `dances`.

| Field | Notes |
|---|---|
| `_id` | String (hex). Converted from ObjectId by migration `0001`. |
| `songArtists` | Optional `[{ song, artist }]`. Scraped song info from copperknob, set by the bulk import in `line-dance-manager-admin`. See decision 7. |
| `stepsheet` / `stepsheetUrls` | Optional. `stepsheetUrls` is an array of source URLs; `stepsheet` is unique-indexed. |
| `primaryTrack` / `tracks` | Track ids in `tracks`. |

**Observed, to confirm:** all 796 dances with `songArtists` have a `primaryTrack`, but it is a 24-character id (Spotify ids are 22). They share 772 distinct tracks, and every one of those tracks is a placeholder (empty `uri`). This suggests the import creates a stub track per dance rather than leaving `primaryTrack` empty. The future matching process would replace those stubs with real Spotify tracks. 785 of the 2,186 tracks have an empty `uri`.

**Other `primaryTrack` gaps:** 41 dances have an empty `primaryTrack` (none have `songArtists`), and 1 ("Backstreet Attitude") points at a track that doesn't exist.

**Open:** how to tell a stub track from a real one (empty `uri`?), and whether `primaryTrack` should be allowed to be empty for unmatched dances (41 non-import dances already have it empty).

## Stephen's class schedule (`bld`)

The source of `ldco-lessons` (decision 18); `bld` is dropped once the admin and the personal site read `ldco-lessons`. Kept here to explain where the data came from.

How the personal site (`dance-folly-website`, beyondlinedance.com) and the admin's BLD pages model Stephen's teaching. Decision 15 records the rules.

| Collection | One document is | Example |
|---|---|---|
| `bld.event_types` | A recurring class at a venue: title, level, price, default start time and duration. Has an on/off switch (`isActive`). | "Charlies Country" at Charlie's Denver |
| `bld.frequencies` | When an event type repeats: weekly on given days (`byDay`), or monthly on the nth weekday (`nth`, `weekday`). Optional start and end dates, and its own on/off switch. | Every Monday, Wednesday and Thursday |
| `ldco.venues` | The venue that hosts it (shared with line-dance-manager since migration `0012`). `event_types.venueId` points here. | Charlie's Denver |
| `bld.events` | One dated occurrence of an event type, with start time, duration, a substitute or cancellation note, and the planned `lessons`. | Charlie's on Monday 2026-10-12 |
| `bld.events.lessons` (embedded) | The plan for that night: one entry per teaching slot (time, dance, level, link, `committed`). | 7:00 PM, "Copperhead Road", committed: false |
| `bld.event_templates` | A reusable lesson plan for an event type, used to prefill an event's `lessons`. | Charlie's default 3-slot plan |
| `bld.lessons` | History: one dance actually taught at a venue on a date. Written when an event's lessons are committed. | "Copperhead Road" at Charlie's Denver, 2026-10-12 7:00 PM |

**Projected and planned events.** An event exists in one of two ways:
- **Projected:** computed on the fly from a running frequency and never stored. The personal site shows these so the calendar fills forward without anyone creating documents.
- **Planned:** stored in `bld.events`, either generated from the frequencies by the admin (generate-events) or created as a one-off. An event is stored once you want to attach a lesson plan, a substitute or a cancellation to it.

**From plan to history.** The admin's "commit lessons" step takes an event's uncommitted `lessons`, marks them `committed`, and writes one `bld.lessons` document each: the date and time, the dance (`danceId`, or `danceName` if it isn't in the catalog), and the venue's **name as text**. That last part means `bld.lessons` doesn't follow venue renames. Old entries also carry labels such as "Barnum Rec Center - Tuesdays" or "Ladies Night at Stampede", and the dance page matches them to venues by name prefix.

**Turning a class off.** Switch the event type (or just one frequency) off in the admin. It then stops being projected, its stored future events are hidden, and its venue drops out of "current venues". Its history in `bld.lessons` stays, so the venue still appears in the dance page's history filter. End dates are optional and only needed if you want a class to stop on a known date.


## DJ Feed attendance and lessons (`djfeed`)

Decision 20. Written by line-dance-dj-feed; moved from `ldco` (`session_attendance`, `host_dancers`) or new (`feed_lessons`).

| Collection | One document is | Key fields |
|---|---|---|
| `session_attendance` | A signed-in dancer at a host's live DJ Feed event | `sessionId`, `hostId`, `userId`, `firstSeenAt`, `lastSeenAt`; unique (`sessionId`, `userId`) |
| `host_dancers` | One host and one dancer, summarising the above | `hostId`, `userId`, `firstSeenAt`, `lastSeenAt`, `sessionCount`, `lastSessionId`; unique (`hostId`, `userId`) |
| `feed_lessons` | A dance a host ran as a lesson block at an event | `sessionId`, `hostId`, `danceId`, `startedAt`; unique (`sessionId`, `danceId`) |
| `lesson_checks` | A dancer's answer about a wishlisted dance they were taught | `userId`, `feedLessonId`, `answer` (`known` / `refresh` / `not_taken`), `answeredAt`; unique (`userId`, `feedLessonId`) |

`hostId` is the host's user id: the same id as `ldco.instructors.userId` when the host is an instructor. Ids are strings (`new ObjectId().toString()`) and times UTC Dates.

**Contract 0.17, declared ahead of the next infer.** The DJ Feed writes these and the last inference didn't see them: `dj_requests.lessonPhase` (string or null, and older requests omit it); `session_reports.playedTracks[].lesson` (a string or a boolean, or null; not every played row is a lesson); `dj_sessions.extensions` (optional array, same as the report's `extensions`, whose items are still unknown); `dj_sessions.durationMinutes` may be null.

**A feed lesson isn't a taught lesson.** `ldco-lessons.lessons` is the source of truth for what was taught. To find the dancers at a taught lesson: its `instructorId` → `ldco.instructors.userId` (= `hostId`), the same `danceId`, and the same local date (the lesson event's `timeZone`) → the feed lesson's `sessionId` → `session_attendance` rows for that session. `$lookup` can't cross databases, so the join runs in app code.

## Instructor schedule (`ldco-lessons`)

Decision 18. Any instructor's schedule, in its own database. Migration `0013` created it from `bld` (the section above), keeping `bld`'s collection and field names with the approved changes. Venues, instructors and `instructor_venues` stay in `ldco`.

| Collection | One document is | Key fields |
|---|---|---|
| `event_types` | A recurring event at a venue | `venueId` (`ldco.venues`), `title`, `level`, `price`, `defaultStartTime` (`HH:mm`, local), `defaultDurationMinutes`, `isActive`, `createdBy` (instructor id, final say), `verifiedAt` / `verifiedBy` |
| `frequencies` | When an event type repeats | `eventTypeId`, `kind`: `WEEKLY` (`byDay`: `MO`…`SU`) or `MONTHLY_NTH_WEEKDAY` (`weekday`, `nth`); `startTime` (`HH:mm`, local), `durationMinutes`, optional `startDate` / `endDate` (`YYYY-MM-DD`), optional `isActive` (missing = on) |
| `events` | One stored event | `eventTypeId` (absent for a special event), `date` (local `YYYY-MM-DD`), `startAt` / `endAt` (UTC Dates), `timeZone`, `isCancelled`, `cancelNote`, `substitute` (name), `substituteInstructorId`, `specialNote`, `lessons[]`, `verifiedAt` / `verifiedBy` |
| `events.lessons` (embedded) | One lesson planned or taught that day | `_id`, `startAt` (UTC, or null for no time yet), `dance` (name) and/or `danceId`, `level`, `link`, `committed` (taught), `skipped` |
| `lessons` | History: one dance taught | `danceId` or `danceName`, `venue` (the name as written), `date` (UTC Date), `instructorId`, `venueId`, `eventId` (when known), `lessonId` (the `events` lesson it came from; null on migrated rows) |
| `event_templates` | A reusable lesson plan for an event type | `name`, `isDefault`, `lessons[]` with `time` (`HH:mm`, local), `dance`, `level`, `link` |
| `event_instructors` | An instructor teaching an event type or a special event | `instructorId`, and one of `eventTypeId` / `eventId`; `role`: `creator` or `co-instructor` |
| `event_instructor_requests` | A request to co-teach, waiting for the creator | `instructorId`, one of `eventTypeId` / `eventId`, `requestedBy` (user id), `createdAt` |

**A lesson's state** is `committed` (taught), `skipped`, or neither (planned). "Changed" is editing a planned lesson before marking it taught.

**Special events** are `events` with no `eventTypeId`; they carry `venueId`, `title` and `createdBy`, and their instructors are `event_instructors` rows with an `eventId`. An event that runs several days just has a later `endAt`.

**Finding an instructor's schedule:** their `event_instructors` rows → those `event_types` (and special `events`) → the types' `frequencies` and stored `events`. Projected dates come from running frequencies (decision 15's rule), matched to stored events on `eventTypeId` + `date`. Venue and instructor names come from `ldco` in a separate query (no `$lookup` across databases). The personal site does the same for Stephen's instructor id.

**History:** `lessons.instructorId` and `venueId` are recorded when a lesson is marked taught, so later changes to who's linked don't rewrite it. 786 of the 1,579 migrated rows were matched to the exact event (one stored event at that venue containing the time); the rest predate stored events. `venue` keeps the label as written ("Barnum Rec Center - Tuesdays"), and `venueId` maps it to the venue. 779 migrated dates were an hour off (the admin's hardcoded `-07:00` during daylight time) and were corrected. A history query must never filter on an empty `lessonId`: migrated rows have none, so it would match all of them.

**Declared in contract 0.17** (`src/contract/declared-fields.ts`; the generator keeps these expressions, so a sample that only has nulls can't narrow them again):
- `events` for a special event: `eventTypeId` may be absent or null; optional `venueId`, `title` and `createdBy`.
- `events.substituteInstructorId` is a string or null.
- `lessons.lessonId` is a string or null.
- `event_templates.lessons.link` is a string or null.
- `verifiedAt` is a Date or null and `verifiedBy` is a user id or null, on `event_types` and `events` here and on `ldco.venues` and `ldco.lessons` (decision 17).

**Still not in the generated shape.** No document in the last inference showed these, and 0.17 doesn't guess them:
- `events.lessons.startAt` as `null` for a lesson with no time yet (it stays a Date).
- `event_instructors` rows with `eventId` instead of `eventTypeId`.
- `event_instructor_requests` documents (the collection is empty).

## Copperknob alerts (`copperknob_alert`)

A watch rule matches the new-dance feed on a dance name, and optionally a choreographer (`choreographer` may be omitted). `notifyWebhookUrl` is where a match is posted; rules created before that field omit it. `processed_items.details.choreographer` is a string and may be empty when the feed item named no choreographer.
